# 图片解读、图文策划与多日排期规范

本规范是 `douyin-rpa-publisher` 的图片策划合同。图片分析由 Codex 完成；本地发布器只读取七字段文件名并执行离线校验、演练和发布。策划内容可参考抖音、快手图文风格，但本项目的自动发布范围仍仅限已授权的抖音账号和批次。

## 1. 硬约束优先级

以下约束直接关系到现有脚本和抖音发布门禁，优先于文案建议：

1. 每个新批次必须由用户明确提供开始日期。用户说“明天”或“周五”时可转换成明确日期；没有日期时停止，不默认猜测下一天。
2. 发布标题推荐 8—15 个字符，硬上限为 15 个字符。不得使用 16—18 字标题，否则七字段复制和发布校验会失败。
3. 每张图片独立成为一条内容；严格 3 个话题；整批 BGM 及原版、DJ、翻唱、加速、慢速等变体不得重复。
4. 每天最多 3 条；同一日期和时间不得重复；发布时刻必须符合抖音当前“至少 2 小时后、最多 14 天内”的平台窗口。
5. 原图保留在 `待发布-素材`，只把像素和 EXIF 完全不变的重命名副本写入 `已重命名-素材`。

## 2. 账号定位与表达边界

- 内容方向：成熟女性生活随拍、下班后生活、独处日常、日常陪伴和温柔克制的情绪表达。
- 主要受众：31—50 岁男性用户。
- 整体风格：成熟、自然、温柔、真实、有生活感和轻微故事感；可以有克制的暧昧感，但不得低俗、露骨、擦边或物化人物。
- 可以根据可见的神态、动作、穿着、光线、生活场景、独处状态和成熟气质策划内容。
- 不得编造感情经历、婚姻、家庭、长期单身、缺爱、失恋等图片无法确认的背景。

## 3. 整批分析与排序

先检查所有尚未处理的图片，再统一排序和排期，不按文件名或上传顺序机械发布。每张图内部分析：

- 场景、光线、时间感；
- 人物神态、视线、动作、姿态；
- 穿着风格、成熟气质和生活状态；
- 情绪轻重、故事感和适合的内容方向；
- 与其他图片在场景、穿着、动作、标题结构、话题和 BGM 上的相似度；
- 最适合的上午、下午、傍晚或晚上时段。

保留两套编号：`图片NN` 始终对应原始图片顺序，`第NN条发布内容` 对应最终发布时间顺序。最终计划和聊天输出均按发布时间排序，不得遗漏、重复或合并图片。

## 4. 发布频率与时段

默认每天 3 条，按上午、下午、晚上形成节奏；最后一天不足 3 条时只安排最合适的时段，不补足数量。日期从用户提供的开始日期起连续使用自然日。

- 上午 `09:30—11:20`：自然光、早餐、咖啡、通勤、出门、明亮室内、轻松穿搭和轻情绪。
- 下午 `14:00—17:30`：午后阳光、窗边、咖啡馆、商场、街边、室内休息、穿搭和人物气质。
- 傍晚 `17:30—19:20`：下班前后、傍晚街拍和回家路上。
- 晚上 `20:30—22:50`：夜景、路灯、车内、暖光、晚餐、回家、独处、陪伴和较强故事感。

分钟必须自然变化。不得把明显夜景排在上午，也不得把明亮日常机械排到深夜。同一天避免三张同场景、同套衣服、相似动作、全夜景、全强伤感、同结构标题或相似 BGM。

## 5. 每张图片的策划字段

每张图片必须生成以下字段，并写入结构化计划 JSON：

1. `source_path`：原始图片完整路径。
2. `image_number`：原始图片编号，重排后不得改变。
3. `publish_number`：最终发布时间顺序编号。
4. `title`：1 条自然口语标题，推荐 8—15 字，硬上限 15 字。混合生活记录型、画面触发型、克制心声型、轻互动型和成熟反差型，避免连续相同开头、全部疑问句、卖惨和模板腔。
5. `topics`：恰好 3 个带 `#` 的简短话题，真实相关、便于搜索；同批话题组合不得完全重复。
6. `bgm` 与 `artist`：每图 1 首 BGM 和歌手。综合图片、标题、时段、受众、用户歌单和近期传播度选择。
7. `publish_time`：唯一的 `YYYY-MM-DD HH:mm` 明确时间。

图片的场景、光线、人物状态、穿着、动作和整体气质只用于内部整批判断，不额外输出长内容描述、推荐理由或关键词。

## 6. BGM 选择

- 若工作区存在 `BGM歌曲.txt`，必须读取并优先考虑高度适配项，但不得强行使用。
- 具备联网能力且确需使用“近期热度”时，核对最近 30—60 天的抖音、快手或短视频平台信息；无法可靠核实时使用用户歌单或长期常见且易搜索的歌曲，不伪造热度。
- 优先级：近期流行且高度适配；用户歌单中高度适配；平台常见、好搜、长期适配。
- 同批歌曲绝对不重复；同一首歌的原版、翻唱、DJ、加速、慢速或不同歌手版本均视为重复。
- 同一天的三首歌还应避免风格高度相似。

## 7. 用户可读输出

完成整批策划后，按发布时间顺序为每张图片输出：

```text
━━━━━━━━━━━━━━━━━━
图片X｜第X条发布内容
━━━━━━━━━━━━━━━━━━

标题：
……

话题：
#话题1 #话题2 #话题3

BGM：
《歌名》— 歌手

发布时间：
2026年X月X日 HH:MM
```

不要输出内部长分析过程，不在结尾追问是否继续。

## 8. 结构化计划与七字段副本

结构化计划保存为工作区根目录的 `发布计划-YYYYMMDD.json`，并符合 `docs/image-content-plan.schema.json`。在复制图片前执行：

```powershell
npm.cmd run validate:content-plan -- "<workspace>\发布计划-YYYYMMDD.json" --start-date YYYY-MM-DD
```

结构化计划只包含现有发布字段，不增加长内容描述、推荐理由或关键词。重命名副本继续使用严格七字段：

```text
图片NN-第NN条发布内容-标题-#话题1 #话题2 #话题3-BGM歌名-歌手-YYYY年MM月DD日HH时mm分.原扩展名
```

字段内部不得出现半角 `-`；清理 Windows 非法字符；月份、日期、小时、分钟补零；保留原扩展名。生成副本的外部工具只应读取上述现有发布字段。

## 9. 输出前自检

在生成副本前确认：

1. 图片没有遗漏、重复或合并，原始编号保持正确；
2. JSON 包含每图的原图路径、双编号、标题、3 个话题、BGM、歌手和时间；
3. 标题不超过 15 字；
4. 发布时间升序、不重复、从开始日期连续排期且每天最多 3 条；
5. 三时段与画面时间感匹配，同一天内容有节奏；
6. BGM 及其版本不重复，话题组合不重复；
7. 文件名严格七字段，原图像素、格式和 EXIF 未改变；
8. `validate:content-plan` 和现有批次校验均为 PASS 后，才算策划与重命名完成。
