# 京东反爬机制分析与设计应对

本文档阐述本系统在京东真实反爬环境下**解决的核心问题**、对京东反爬机制的**认知（心得）**，
以及由此衍生的**关键设计权衡**。它回答的不是"系统有多自动化"，而是"在强反爬约束下，
我们如何把采集任务稳定跑通，并从中沉淀了哪些工程经验"。

> 系统实现细节见 [ARCHITECTURE.md](./ARCHITECTURE.md)；运行步骤见 [SETUP.md](./SETUP.md)；
> 详情爬虫的抽取与指纹伪装见 [jd_product_detail.md](./jd_product_detail.md)。

---

## 1. 背景与问题提出

京东是国内反爬力度最强的电商之一。其页面并非静态 HTML，而是大量依赖前端渲染、运行时环境
指纹与行为验证。一个朴素的 `requests` 爬虫在京东上几乎寸步难行：要么拿不到真实数据，
要么很快被风控拦截。

本系统的目标，并非追求"全自动无人值守"，而是在上述真实约束下，把采集链路**稳定、可恢复、
不丢数据**地跑通。因此系统的设计重心是"对抗反爬的工程取舍"，而非"取代人工"。

---

## 2. 系统解决的核心问题

| 问题 | 表现 | 本系统的应对 |
|------|------|--------------|
| **详情页无法用纯 HTTP 稳定采集** | 无头请求拿到空壳页或被直接验证拦截 | 用 DrissionPage 真实 Chromium 内核渲染页面，绕过无头检测（详见第 3 节） |
| **采集频繁中断、前功尽弃** | 验证码 / 空页 / 超时导致整轮作废 | 列表 / 详情双轨解耦 + 状态机（`detail_status`）+ 幂等续爬 + JSON 离线重导，断点可恢复 |
| **验证拦截切断整条链路** | 一次验证码就让无人值守任务卡死 | 人机协作兜底（`wait_for_manual_verify`）：机器跑量，人在回路最后一道，数据不丢 |
| **字段长度 / 结构不稳定导致入库失败** | 标题、参数超长或结构变化使 INSERT 报错 | 动态读取 `INFORMATION_SCHEMA` 按列实际长度截断，并统一两条入库路径 |
| **静默失败掩盖反爬事件** | `except: pass` 吞掉封禁 / 验证码信号 | 异常分层 + 分级日志，使反爬信号"可见"而非被吞没 |

## 3. 对京东反爬机制的认知（心得）

### 3.1 反爬是分层的，列表页与详情页不是一个量级

- **列表 / 分类页**：主要依赖**协议层**防护（请求频率、UA、基础 headers）。用 Scrapy 配合
  合理的请求编排与降速即可稳定获取 SKU 链接。
- **详情页**：进入**行为层**防护（JS 运行时指纹、验证码、登录态）。防护级别显著提升，
  必须换一套技术栈（真实浏览器内核）才能应对。

这正是一套系统要同时保留 Scrapy（列表）与 DrissionPage（详情）两条技术轨道的根本原因——
不是冗余，而是针对不同防护层级的最优解。

### 3.2 协议层对抗在详情页必然失败

详情页的真实性高度依赖**运行时环境指纹**：webdriver 特征检测、canvas / 字体指纹、
请求时序与行为轨迹等。无头 HTTP 客户端在这些维度上"一眼假"，要么返回空数据，
要么立即触发验证。结论是：**详情页采集必须建立在真实浏览器内核之上**，无头方案在此不可用。

### 3.3 验证态 / 登录态是隐形成本

京东对**未登录、新会话**极不友好，触发验证的概率远高于常态登录用户。本系统的做法是复用本地
**已登录的真实浏览器（Chrome/Edge 等 Chromium 内核，通过远程调试端口 9222 接入）**，直接继承其 cookie 与"信任分"，
从而显著降低验证触发率。思路本质是"**借用户环境**"，而非"伪造环境"——后者在京东的风控下
成本更高、更易失效。

### 3.4 节奏比伪装更重要

指纹伪装（navigator 伪装、UA 轮换）有价值，但**速率控制才是防封的第一道防线**。系统刻意采用
单并发（`CONCURRENT_REQUESTS=1`）+ 固定下载延迟（`DOWNLOAD_DELAY=4`）。盲目提高并发不仅不会
更快，反而会自爆式触发风控。在京东场景下，"慢而稳"优于"快而封"。

### 3.5 失败是常态，不是异常

在京东反爬环境下，验证码、空页、重定向、超时**天天发生**，而非偶发。因此系统的核心价值不在于
"更快更强"，而在于**可恢复、幂等、带状态**：

- 任一阶段中断，下次从断点续跑（`detail_status` 状态机 + `--retry-failed`）；
- 详情先落 `data/{sku}.json`，再离线导入 `products`（`--from-json`），已采集成果与浏览器解耦；
- 写入 `products` 使用 `ON DUPLICATE KEY UPDATE` 幂等 upsert，重复运行不产生脏数据。

### 3.6 数据必须做内容级校验

京东有时返回 **HTTP 200 的空壳页 / 重定向页**，而非明确的 404。若仅以状态码判断成功，会入库
"假商品"（标题 / 品牌为空）。系统对此的处理是：当核心字段抽取为空时，判定爬取失败
（`run()` 返回 `None`），由上层标记为 `detail_status=2`，而非生成残缺记录。

## 4. 关键设计权衡

### 4.1 双轨技术栈（Scrapy + DrissionPage）

列表采集用 Scrapy（协议层、高吞吐、低成本），详情采集用 DrissionPage（行为层、浏览器渲染）。
两轨仅通过 `product_links.detail_status` 一个字段握手，互不影响进度，也互不放大风险——
列表的"廉价扫描"不会被详情的"昂贵渲染"阻塞。

### 4.2 人机协作（`wait_for_manual_verify`）的定位

这是常被误解的一点。在评估过**全自动破解验证码的投入产出比**之后，系统选择把人留在回路的
最后一道：批量模式（`--db`）默认不等待验证（避免无人值守卡死），单 URL 模式默认等待人工完成。

这不是系统的短板，而是**"验证破解成本远高于人力成本"时的务实工程取舍**——它恰恰体现了对
反爬现实成本的清醒认知：在验证码这一层，与其投入不稳定的破解逻辑，不如用极低的人力成本兜底，
保证整条链路不丢数据。

### 4.3 解耦优先于"一体化"

系统没有把所有阶段塞进一个 Spider，而是以数据库为 boundary 切成可独立运行、可独立重试的阶段。
其出发点是第 3.5 节的判断——**失败是常态**。解耦使每个阶段都能独立恢复，整体鲁棒性远高于
一个"看起来更自动"但一崩全崩的单体流程。

---

## 5. 小结

本系统在京东反爬环境下的工程贡献，可归纳为三点：

1. **用对工具**：协议层用 Scrapy，行为层用真实浏览器内核，按防护层级匹配技术栈；
2. **把不确定留给人**：在验证码这一高成本环节，以人机协作换取链路稳定性；
3. **为失败而设计**：双轨解耦、状态机、幂等续爬、离线重导，使采集在频繁中断中仍能向前推进。

这三点共同构成了系统应对京东反爬的完整方法论。
